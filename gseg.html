01 Overview

The problem: incident data scattered across spreadsheets, without standardization, without geospatial visualization, and with little analytical capacity. Identifying territorial patterns relied on manual reading and isolated data interpretation.

G-SEG centralizes these incidents, geocodes records against address registries, and turns historical data into territorial visualizations that can actually be used for spatial analysis and hotspot identification.

The platform is designed for different analytical contexts — from users who need to explore incidents individually to consolidated views for quick reading of territorial patterns and event concentration.

02 Architecture

A linear pipeline, on purpose. Raw data goes in, geocoded incidents come out, and the frontend is a thin layer over PostGIS queries.

03 Key features

Smart data import

An optimized pipeline processes 42,000+ SEGUP incidents in ~19 seconds, with duplicate detection, geographic validation, and automatic precision classification (High / Medium / Low).

Georeferenced crime map

Interactive Mapbox GL JS visualization displaying real incidents across Belém, with neighborhood polygons and street coloring by risk level computed via PostGIS.

Chained filters

Filter by neighborhood, period, crime nature, and geocoding precision — applied as a single PostGIS query on the server.

Per-neighborhood analytics

Ranking of neighborhoods by incident volume with period filter, sorted by criminality descending.

Report export

CSV and PDF report generation with filtered data, formatted for analysis and briefings.

Admin panel

Dedicated interface for spreadsheet imports, post-import routines (snap-to-road, cleanup of clustered coordinates, precision classification), and log monitoring.

05 Challenges
01

Imprecise geocoding of raw data

SEGUP spreadsheets contained generic coordinates — many crimes registered at the precinct or battalion HQ rather than at the actual incident location. Naive geocoding artificially inflated certain streets and neighborhoods.

SolutionA precision score per record (HIGH / MEDIUM / LOW) based on the density of repeated coordinates. The map filters by score and analysts know exactly which pins to trust.
02

Importing 42,000 records crashed the server

The initial pipeline fired thousands of sequential queries against the database — one per spreadsheet row. With 42k records, imports took minutes and exhausted the connection pool.

SolutionFull preload into memory before the loop — neighborhoods, streets, and duplicate keys loaded once via HashSet. Zero queries inside the loop. Result: 42,000 crimes imported in ~19 seconds.
03

Clustered coordinates inflating the street ranking

Crimes with imprecise locations shared the exact same coordinate, making certain streets appear as the most dangerous in the city due to artificial point accumulation.

SolutionA cleanup routine by density threshold — coordinates with 5 or more identical crimes are unlinked from the street, keeping the crime in the database but removing it from the ranking. Per-street analysis reflects only trustworthy locations.
